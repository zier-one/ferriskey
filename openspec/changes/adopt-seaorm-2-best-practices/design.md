# Design

## Context

See `proposal.md` - Why. The current dependency and architecture facts that shape this design are:

- `sea-orm 2.0.4`, `sea-query 1.0.2`, and `sqlx 0.9.0` are already unified in the dependency graph.
- `core/src/entity/` contains 73 entities: 72 expanded entities and one compact entity. All 73 have empty `ActiveModelBehavior` implementations and none uses relation-level custom conditions.
- The current schema contains 75 tables. `security_event_chain_heads` and `user_token_revocations` are intentionally SQL-only internal tables.
- There are about 688 `Entity::Column` references, five `find_with_related` / `find_also_related` call sites, about 20 manual transaction starts, and about 25 raw `Statement` construction sites.
- Code generated by the dense Entity format can add relation fields to `Model`; only two production code paths currently construct an entity `Model` directly.
- FerrisKey uses a hexagonal architecture. SeaORM must remain confined to the entity and infrastructure layers; the domain must not depend on SeaORM.
- SQLx migrations remain the source of truth for the schema. Production schema changes are not part of this refactor.

## Goals / Non-Goals

**Goals:**

- Make new and migrated SeaORM code match the SeaORM 2.0 recommended style.
- Deliver the work as one pull request per usage domain, with each pull request independently reviewable and reversible.
- Preserve SQL generated by existing business operations unless a specific SeaORM API is proven equivalent.
- Preserve the current domain/ports/adapters boundaries and public behavior.
- Keep codegen reproducibility explicit, including documented exceptions for SQL-only internal tables.

**Non-Goals:**

- Entity First, `schema-sync`, or runtime schema management.
- RBAC / `RestrictedConnection`, Arrow / Parquet, SQL Server, or `sea-orm-sync`.
- Replacing high-performance PostgreSQL SQL with ORM queries.
- Refactoring domain behavior, public APIs, database schema, or migration history.
- Creating a separate conventions-only pull request; required checks belong to each pull request.

## Decisions

### 1. Migrate existing entities to the dense SeaORM 2 format in one entity-only pull request

Generate entities from a fresh PostgreSQL database after all SQLx migrations, using SeaORM CLI 2.0.4 with the dense format. Reconcile the generated relation graph before replacing `core/src/entity/`.

Alternatives considered:

- Keep expanded entities: supported, but does not give the project a coherent SeaORM 2-native entity baseline.
- Use `#[sea_orm::compact_model]`: useful as a transitional mechanism, but it retains a legacy source format and adds unnecessary intermediate work.
- Regenerate incrementally per module: reduces individual diffs but leaves incompatible relation-field changes spread across many pull requests and makes this domain harder to audit.

The pull request must not convert `Column` call sites or introduce loader/nested-write behavior. Its only purpose is the Entity format and the resulting compile fixes.

### 2. Keep SQL-only internal tables out of the Entity layer

`security_event_chain_heads` and `user_token_revocations` are intentionally accessed through raw SQL:

- `security_event_chain_heads` requires a single PostgreSQL statement that updates the realm head, computes the next hash, and inserts the audit event without forking the chain under concurrent writers.
- `user_token_revocations` is a performance-sensitive not-before marker. Its upsert uses the database clock, and token validation checks token, user, and session revocation in one statement.

Generating unused entities would imply that ordinary ORM writes are appropriate for these tables. The codegen process therefore needs an explicit exception list for these two tables, with the reason recorded next to the generation tooling or entity module documentation.

Alternative considered: generate entities for full schema parity while retaining raw SQL. This was rejected because an ORM entity does not add value to these internal state tables and can weaken the invariant that they must only be changed through their dedicated SQL paths.

### 3. Adopt type-aware columns selectively

Use `Entity::COLUMN` for typed filters, comparisons, null checks, `IN` predicates, string helpers, and insert/update expressions. Keep the `Column` enum for generic pagination/sorting abstractions such as `SortColumn<E>`, because different typed columns have different concrete wrapper types and cannot be returned from one homogeneous generic method without losing type information.

Alternatives considered:

- Convert every column reference mechanically: not always possible without degrading generic APIs.
- Keep all `Column` references: misses compile-time type safety, which is the main benefit of the new column design.

The pull request must preserve generated SQL semantics and query ordering. Query tests or SQL snapshots should catch accidental changes.

### 4. Use Entity Loader only for object-graph reads

Use Entity Loader where the repository needs a related object graph, multi-level relations, or avoids N+1 queries. It is especially suited to the current `find_with_related` / `find_also_related` sites.

Do not mechanically replace joins or raw queries that:

- use PostgreSQL-specific SQL;
- aggregate or paginate with custom expressions;
- already batch related rows explicitly;
- are performance-sensitive write paths.

Alternatives considered: replace all joins with Entity Loader. Rejected because some queries need SQL semantics or performance characteristics that the loader is not intended to express.

### 5. Restrict Nested ActiveModel to true aggregate writes

Use Nested ActiveModel only when the parent and children form one aggregate and SeaORM can preserve the existing transaction, ordering, conflict, and cascade semantics. Candidate areas must be selected from code paths that currently perform multi-step parent/child writes and have behavioral tests.

Keep the following on their existing paths:

- Compass `UNNEST` batch writes;
- webhook delivery outbox operations;
- SeaWatch hash-chain writes;
- access and refresh token hot paths;
- any query where SQL statement count, lock scope, or database clock behavior is part of the contract.

Alternative considered: replace most manual `ActiveModel` construction. Rejected because many of those writes are intentionally optimized SQL paths, not aggregate persistence.

### 6. Convert manual transactions only when the closure API preserves behavior

Prefer `ConnectionTrait::transaction` for ordinary multi-statement repository operations. Preserve explicit `begin` / `commit` where the code needs an intentionally long-lived transaction object, savepoint control, or a concurrency test's explicit lock lifetime.

The transaction pull request must preserve isolation behavior, row locks, error mapping, and rollback guarantees. PostgreSQL-backed concurrency tests are required for affected repositories.

### 7. Standardize raw SQL and connection boundaries only where they improve safety or reuse

Prefer parameterized raw SQL and `DbErr::sql_err` / `SqlErr` where common errors need classification. Reusable helpers may accept `ConnectionTrait` when they must work with both a pool and a transaction. New raw SQL may adopt `raw_sql!` when it improves readability without changing behavior.

Do not rewrite PostgreSQL-specific CTEs, `UNNEST`, locking clauses, clock expressions, or audit-chain SQL merely to use an ORM API.

### 8. Keep SQLx migrations as the schema source of truth

Entity generation reads from a migration-built database, but runtime schema sync and Entity First are not enabled. This preserves deterministic production migrations and avoids application-startup schema discovery.

## Risks / Trade-offs

- [Dense codegen changes every entity and adds relation fields] -> Generate from a fresh migrated database, audit the relation graph, keep the pull request behavior-free, and rely on compile errors plus integration tests to expose direct `Model` construction.
- [Generated entities may differ from hand-maintained relations] -> Inventory all `Relation` variants and `Related` implementations before replacement, and reject generation that drops a relation.
- [Type-aware column migration touches many call sites] -> Keep `Column` for heterogeneous generic APIs, preserve SQL tests, and avoid behavior changes in the same pull request.
- [Entity Loader changes query shape and relation ordering] -> Add query-count and deterministic-order assertions for affected reads.
- [Nested ActiveModel changes statement count, lock scope, and cascade behavior] -> Limit it to tested aggregate writes and keep optimized raw paths unchanged.
- [Transaction closure conversion can alter early-return rollback behavior] -> Require rollback and concurrency tests for every converted transaction.
- [The Entity or Column pull request may become too large for the 20-minute review guideline] -> Keep each pull request single-purpose and, if necessary, split its commits or merge sequence mechanically by bounded context without changing the overall domain order.
- [Raw-only tables could be mistaken for missing entities] -> Record them in the codegen exception list and document why ORM access is intentionally not provided.

## Migration Plan

1. Pull request 1: dense Entity conversion, relation audit, compile fixes, and codegen reproducibility with the two documented raw-only exceptions.
2. Pull request 2: type-aware column adoption while preserving generic sorting abstractions.
3. Pull request 3: transaction closure adoption for eligible repository operations.
4. Pull request 4: Entity Loader adoption for selected related reads.
5. Pull request 5: Nested ActiveModel adoption for selected aggregate writes.
6. Pull request 6: targeted raw SQL and connection abstraction cleanup.

Each pull request is independently revertible and must not contain database migrations. Rollback is a normal code revert; no data rollback or schema rollback is required.

## Open Questions

None. Candidate repositories for Entity Loader, Nested ActiveModel, and transaction conversion will be selected during their respective implementation pull requests from the audited call-site inventory.
